Ex 1 :

Pourquoi créer le dépôt GitHub vide ? Si GitHub y ajoute un README ou un .gitignore, 
il crée un premier commit qui n’a rien à voir avec l’historique du projet cloné. Mon git push 
serait alors refusé, ou il faudrait fusionner deux historiques sans ancêtre commun. Un dépôt vide 
reçoit l’historique tel quel.

À quoi sert upstream ? Il garde le lien avec le dépôt d’origine, alors que origin pointe vers 
mon dépôt. Je peux ainsi récupérer les corrections ou nouveautés de l’enseignant avec git fetch 
upstream puis git merge main, sans toucher à mon travail sur origin.

Ex 4 :

1-
npm run lint lance tsc --noEmit : c’est une vérification des types TypeScript, sans ESLint et sans 
produire de fichiers.
npm test lance vitest run et exécute les tests automatisés.
npm run build produit la version livrable. Dans le backend, tsc compile vers dist/. Dans le frontend, 
il vérifie d’abord les types (tsc --noEmit), puis vite build génère les fichiers statiques.

2-
Le backend compte 20 tests:
6 tests unitaires dans validation.test.ts (règles de validation) qui n’ont pas besoin de la base.
14 tests d’intégration dans app.test.ts qui ont besoin de PostgreSQL. 

Le frontend compte 3 tests (format.test.ts), sans base.

3-
Après npm test, les réservations de démonstration ont disparu : l’interface affiche des réservations
en janvier 2030 à la place. Chaque test d’intégration commence par vider la table (TRUNCATE) puis la 
remplit avec des données de test fixes. Comme les tests utilisent la même base que l’API, ils écrasent 
les données de démonstration. On les retrouve avec npm run db:reset, qui recrée les six réservations 
avec des dates calculées à partir du jour courant.

4- Qu’est-ce qui garantit que chacun lance ces vérifications ?
Rien, seulement la discipline de chacun
